# 07 문서·제출 점검 · 06 이 끝나면 바로(늦어도 화면 남은 30분), 한 요청으로 → 브리핑 → 직접 읽기

- 마지막 `/new` 뒤 탭 1 요청이 4번을 넘었으면 이 카드 전에 `/new` → 1(Use current Git worktree. 2 는 다른 폴더 복사본이라 커밋이 거기 쌓인다) → 아래 줄 추론이 medium 인지 보고(아니면 `/model`) 붙인다. 브리핑·모의 질문은 그 대화에서 이어 간다

```
$verify-submit 목표: 문서·제출 점검을 한 번에 해. README(실행 한 줄·구조·결과 숫자·한계)·DECISIONS·STATUS 를 실제 출력과 git log 에 맞춰.
맥락: 화면 타이머 남은 <분>분(15분 남으면 제출 시작). 사람 확인: <CARDS.md 에 모아 둔 last.sh 숫자 · 화면에서 본 칸 · 실무자에게 다시 확인받은 숫자 · 탭 2 지적 판단>.
제약: 새 기능 금지, 5분 안에 못 고칠 것은 목록으로만(위에서 받아들인 탭 2 지적은 5분 안이면 가장 작게 고치고 처음 그 검사로 다시 통과). 실험 파일·복사본·작업 폴더에 복사해 놓고 안 쓴 틀은 지우고(.agents 는 건드리지 마, 막히면 '쓰지 않음' 한 줄), git diff 로 사람이 모르게 바뀐 문서 줄이 없는지 봐. DECISIONS 방법 줄 이름은 코드의 실제 단계와 맞추고, 과제의 AI 협업 문서가 있으면 위 사람 확인과 DECISIONS 사람 줄을 그 칸에 옮겨(사람이 한 일을 미확인으로 쓰지 말고, 사람 확인이 git log·VERIFICATION 과 어긋나면 실제 커밋대로 쓰고 답에 '어긋남:' 한 줄). 깨끗한 clone(mktemp)에서 README 명령을 그대로 돌리고(서버는 검사 스크립트 안에서 PORT=0), 대상일·기간을 요청·인자로 받으면 다음 날로 한 번(앞 결과·확정이 다음 계산에 들어가나 · 대상·처리·남은 수 · 확정 같은 다음 단계가 되나 · 걸린 초)과 데이터 시작 전 날짜로 한 번(응답 코드), 아니면 그 clone 의 data 에 다른 파일에 없는 키 한 줄·처음 보는 값 한 줄을 넣어 한 번(종료값 · 출력 파일이 새것인지 · 행 수)과 행을 2배로 한 번(걸린 초) 돌려 VERIFICATION 한 줄(이 실행 결과로는 코드를 고치지 마).
완료: 커밋 뒤 git status --short 가 비면 끝. 답은 점검 결과 5줄(DECISIONS 를 고쳤으면 `정한 것:` 줄 포함).
```

점검이 끝나면 같은 탭에 브리핑 한 번(늦어도 화면 남은 25분). 파일로 남기지 않는다.

```
브리핑: 제출물(코드 포함)·docs/DECISIONS.md·git log 기준으로 내가 AI 없이 설명할 수 있게 정리해 줘. 파일은 만들지 마. ① 문제·성공 기준·결과 숫자(지금 방식 숫자와 나란히 · 순위·목록을 내면 상위 3개 이름과 점수 · 못 채운 건이 남으면 몰린 날짜·대상과 그 까닭 숫자(그날 필요·가능 수) · 사람·설비에 나누는 과제면 가장 많은·적은 쪽 횟수) ② 방법 수준(정확해·휴리스틱·규칙 가운데 무엇 · 처리 순서 기준과 하나를 고르는 점수 · 점수·제약에서 뺀 항목 · 개선 단계가 있으면 단계마다 개선으로 받는 조건·시도하지 않는 옮기기·개선 뒤 다시 시작하는 곳 · 멈춤 조건과 실측 실행이 실제로 멈춘 조건(수렴·시간)·시간 상한이 걸리는 단계·실측 초 · 왜 · 버린 대안이 안 되는 이유는 이번에 돌린 이전 판·기준선 숫자로, 없으면 '잰 숫자 없음') ③ 구조와 데이터 흐름: 요청·명령 하나마다 거치는 파일:함수 차례 · 시작 때 한 번 읽는 것 · 상태 위치(DB 표·열 · 메모리 · 파일)와 그 경로의 기준(코드 위치·실행 폴더) · 재시작 뒤 남는 것 · 서버·DB 가 있으면 무거운 계산이 트랜잭션·잠금 안인지 밖인지, 번호와 최신을 정하는 열, 수정·확정 때 이전 판(덮어씀·이력) · 왜 이 구조 ④ 그 밖에 결과를 바꾼 결정 전부(Codex 가 혼자 정한 것 포함): 무엇(넣은 값·뺀 값과 건수 · 값이 비는 행이 생기면 그 건수와 계산에 실제로 들어가는 값) · 왜(추정뿐이면 '기록된 이유 없음') · 버린 대안(없으면 '없음') · 정한 쪽, 요청을 거절하는 규칙은 하나씩 정한 쪽과 함께 ⑤ 구현·검증한 것(명령·숫자 · 그 검사가 실제로 대조하는 범위 · 구현 함수를 불러 쓰는지)과 가정으로 둔 것 ⑥ 실무자 답마다 코드에서 한 일(바꾼 것 · 그대로 둔 것 · 걸린 행 수) ⑦ 실패마다 상태 코드(CLI 는 종료값)·문구와 출력 파일 상태 · 입력 파일끼리 키가 안 맞거나 처음 보는 값일 때 · 프로세스가 죽거나 저장이 실패한 뒤 상태 · 서버·DB 가 있으면 같은 요청을 한 번 더 보낼 때 저장되는 것과 응답, 잠금 밖에서 바로 답하는 요청과 긴 계산 중 기다리는 요청, 같은 대상 동시 수정 두 건일 때 두 번째 결과 · 입력이 10배이거나 날짜가 바뀌면(점검에서 돌린 숫자로) 먼저 깨지는 곳(상한 없는 단계 · 코드에 박힌 날짜·상수 파일:줄) ⑧ AI 제안을 받아들임·고침·버림 사례 2건(근거 숫자 · 오류가 들어간 커밋과 그동안 안 보인 이유 · 처음 드러난 때 · 고친 커밋과 고친 뒤 결과 숫자 · 고친 뒤에도 못 잡는 것) ⑨ 약한 곳마다 파급(누가 무엇을 잘못 보게 되나)과 다음 검증. 35줄 이내, 한 줄에 한 가지, 한국어로만(한자·일본어 글자 없이).
```

- 브리핑을 10분 읽는다. 모르는 줄은 `<그 줄>은 왜? 3줄로, 고치지 말고` 를 한두 번 묻는다. 그다음 화면을 보지 않고 방법·구조·약점을 4문장으로 쳐서 끝에 `사실과 다른 곳과 내가 빠뜨리거나 모른다고 한 결과 이름·숫자만 짚어, 파일은 고치지 마` (2분, 서술형 연습)
- 화면이 20분 넘게 남으면 제출 전에 탭 1 에 아래 모의 확인 질문을 붙이고, 문항마다 화면을 보지 않고 2~3문장으로 답해 보낸다(6문항 약 12분. 짚인 곳은 브리핑에 없던 세부라 CARDS.md 에 한 줄로 적어 두고 제출 뒤 대기 때 다시 본다). 그보다 적게 남으면 ③·⑦ 처럼 짧았던 칸마다 `<그 칸>은 왜? 3줄로, 고치지 말고` 를 한 번씩 묻고, 탭 3 에서 핵심 파일을 직접 열어 함수 이름·상태 코드를 본다(답할 때는 코드를 못 본다)

```
모의 확인 질문: 제출물(코드 포함)·docs·git log 로 내가 AI 없이 설명할 수 있는지 볼 질문을 한 번에 하나씩 내. 차례는 방법 선택 · 구조와 흐름 · 구현과 가정 · 실패·동시 수정 · 조건 변화 · AI 협업, 문항마다 브리핑에 한 줄도 없는 것(남은 실패·못 채운 건의 실제 행 · 계획 커밋과 달라진 구현 · 문서끼리 어긋난 곳 · 잡지 않는 예외 · 키가 안 맞거나 처음 보는 입력 · README 실행 명령 뒤 남는 상태 가운데)을 코드·데이터에서 한 번 확인하고(파일:줄·상태 코드·행·숫자) 내. 내 답이 오면 사실과 다른 곳과 빠진 숫자만 2줄로 짚고 다음 질문. 한국어로만, 파일은 고치지 마.
```

- 확인 질문은 제출물과 작업 기록으로 만들어지고 AI·복사·붙여넣기 없이 문항당 5분, 답할 때 코드를 볼 수 없다. 제출 확정 뒤 질문 준비 대기(최대 10분)는 답 시간이 아니니 브리핑 핵심(방법 · 구조 · 숫자 · 약점)을 되짚는다. '문제 풀기'를 눌러야 첫 문항 타이머가 시작된다
- 답 쓰는 틀: ① 결론 한 문장 ② 이유 두 가지(실무자 답·데이터 숫자) ③ 버린 대안과 이유(검토한 대안이 없었으면 "따로 검토한 대안은 없었습니다") ④ 확인 방법과 숫자 ⑤ 약점(파일·숫자) → 파급 → 다음 검증(명령·지표) · 5분이 모자라면 결론 · 약점 · 다음 검증 세 문장만 · 답마다 파일 이름 하나와 직접 본 숫자 하나 · 질문 전제가 실제와 다르면 첫 줄에 "실제로는 ~로 구현했습니다" · 맡긴 일도 "Codex 에 ~를 맡기고 ~로 확인했습니다" · 기록에 없는 이유는 만들지 않는다: "기록된 이유는 없습니다. 제 이해로는 ~" · 문서 문구는 마지막 커밋 판(브리핑)만 근거로 든다(작업 중 last.sh 로 본 옛 문구는 지워졌을 수 있다)
