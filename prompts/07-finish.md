# 07 문서·제출 점검 · 제출 30분 전, 한 요청으로 → 브리핑 → 직접 읽기

```
$verify-submit 목표: 문서·제출 점검을 한 번에 해. README(실행 한 줄·구조·결과 숫자·한계)·DECISIONS·STATUS 를 실제 출력과 git log 에 맞춰.
맥락: 제출 마감 <시각>. 제약: 새 기능 금지, 5분 안에 못 고칠 것은 목록으로만. 깨끗한 clone(mktemp)에서 README 명령을 그대로 돌려(서버는 검사 스크립트 안에서 PORT=0).
완료: 커밋 뒤 git status --short 가 비면 끝. 답은 점검 결과 5줄(DECISIONS 를 고쳤으면 `정한 것:` 줄 포함).
```

점검이 끝나면 같은 탭에 브리핑 한 번(제출 15분 전). 파일로 남기지 않는다.

```
브리핑: 제출물·docs/DECISIONS.md·git log 기준으로 내가 AI 없이 설명할 수 있게 정리해 줘. 파일은 만들지 마. ① 문제·성공 기준·결과 숫자 ② 결과를 바꾼 결정 전부(Codex 가 혼자 정한 것 포함): 무엇(평소 값·기준선은 넣은 값·뺀 값까지) · 왜(숫자·실무자 답, 추정뿐이면 '기록된 이유 없음') · 버린 대안(검토 안 했으면 '없음') · 정한 쪽 · 남은 위험 ③ 검증 방법과 숫자 ④ 실무자 답마다 코드에서 한 일(바꾼 것 · 그대로 둔 것 · 걸린 행 수) ⑤ 약한 곳·남은 위험. 25줄 이내, 한 줄에 한 가지.
```

- 브리핑을 10분 읽는다. 모르는 줄은 `<그 줄>은 왜? 3줄로, 고치지 말고` 를 한두 번 묻는다. 확인 질문은 제출물과 작업 기록으로 만들어지고 AI·복사·붙여넣기 없이 문항당 5분이다
- 답 쓰는 틀: ① 결론 한 문장 ② 이유 두 가지(실무자 답·데이터 숫자) ③ 버린 대안과 이유(검토한 대안이 없었으면 "따로 검토한 대안은 없었습니다") ④ 확인 방법과 숫자 ⑤ 한계 한 줄 · 질문 전제가 실제와 다르면 첫 줄에 "실제로는 ~로 구현했습니다" · 맡긴 일도 "Codex 에 ~를 맡기고 ~로 확인했습니다" · 기록에 없는 이유는 만들지 않는다: "기록된 이유는 없습니다. 제 이해로는 ~"
- 요청이 8번을 넘었으면 `/new` → '어디서 실행'(Where should the new conversation run?) 창이 뜨면 1(Use current Git worktree) → 빈 입력 칸이 보인 뒤 붙인다(2 는 다른 폴더 복사본이라 커밋이 거기 쌓인다. HANDOFF 없이 docs·git log 로 충분)
