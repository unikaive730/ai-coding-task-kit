# 과제 파악과 실무자 인터뷰

실무자는 묻는 것만 답하고 요구를 한 번에 다 알려 주지 않는다('할 일을 순서대로 알려 달라' 같은 통째 요청은 통하지 않는다). 데이터에서 본 행·값으로 좁힌 닫힌 질문에 답한다. 첫 메시지는 2~3개, 나머지는 답이 오면 한 메시지 3개 이하로 바로 보내고 Codex 에는 모인 답을 한 번에 붙인다(한 메시지에 질문이 넘치면 앞 몇 개만 답이 온다). README 에 적힌 구현 명세는 묻지 않고 숨은 운영 제약·예외·경계값을 묻는다.

## 처음 파악
- README(언어별 판이 있으면 둘 다) · 제공 파일 목록 · 연결된 SaaS·MCP 자료 · `docs/DATA_PROFILE.md`(없으면 `python3 .agents/kit/templates/data/profile_data.py <데이터 파일>` 한 번) · 데이터 앞 몇 줄만 읽는다. 큰 데이터와 분야 요약은 통째로 열지 않는다
- `docs/AGREEMENT.md` 과제 요구 표: 필수 기능 · 제출물·파일명 · 실행 방법 · 제약. 칸은 한 줄(40자 안팎), 모르는 칸은 (추정)
- README 의 '이렇게는 안 된다'(금지한 방식)와 이미 적힌 구현 명세는 과제 요구 표로 옮기고 묻지 않는다
- 데이터 점검의 '확인할 것' 가운데 결과를 바꾸는 것만 차이 표에 한 줄씩 옮긴다

## 첫 질문 목록 (우선순위대로 번호, 1~3번에 '먼저', 원문을 답에 그대로, 질문마다 앞에 받는 사람)
1. 성공 숫자: 어떤 지표가 얼마가 되면 성공인지 · 허용 오류
2. 지금 방식의 같은 지표 숫자(기준선): 지금 방식으로 만든 최근 결과에서 그 지표가 얼마인지
3. 결과를 가장 크게 바꿀 업무 규칙·제약 하나(데이터의 행·값을 넣은 예/아니요 꼴)
4~. 하나씩, 한 질문 한 주제:
- README 의 지금 방식 문제·성공 기준 문장마다 그 문제를 실제 값으로 묻는 질문(예: "들쭉날쭉"이면 "한 사람의 근무가 이어진 날 사이에 바뀌는 것은 몇 번까지 괜찮나요?")
- 누가 언제 결과를 보고 어떤 형식이 필요한지 · 이번에 하지 말 것
- 남은 업무 규칙·제약 후보: 사람·설비 사이 나눔(야간·주말·힘든 일 횟수의 가장 많은·적은 쪽 차이 상한) · 꼭 지킬 우선순위 · 자격·전용 · 준비·교체 시간 · 중단 가능 여부 · (웹·도구) 상태 흐름·되돌리기 · 거절할 입력 · (예측·분석) 예측 시점에 쓸 수 있는 열 · 검증으로 나눌 기간 · 목표 둘이 맞설 때 판정 기준점을 고르는 규칙 · 이미 알려진 원인·공정 목표값(레시피·규격) · (LLM·외부 API) 결과가 몇 초 안에 나와야 하나 · 한 번에 몇 건 · 보내면 안 되는 값(이름·사번) · 시험 때 실제 호출 허용 가운데 과제에 맞는 것
- 데이터 묶음 열(조·등급·구역·종류) 값마다 그 묶음에만 있는 제한(예: "B 등급 작업자도 2층 장비를 맡을 수 있나요?")
- 결과를 바꾸는 데이터 해석: 시간대 · 단위 · 중복 · 빈 칸 · 기준값이 바뀐 시점 · 값이 원래 튀는 구간(점검·교체 직후) · 알려진 오류 · 기준일 밖 날짜 가운데 데이터에서 본 것(본 행·값을 넣어서)
- 차이 표 줄마다 질문 번호를 단다('후속 확인'으로 미루지 않는다)
- 지금 방식의 최근 결과 숫자 하나는 사람이 따로 먼저 묻는다

## 다음 질문 (3개 이하, 첫 질문 목록과 같은 꼴)
- 답으로 아직 안 정해진 성공 기준 · 기준선 숫자(못 받았으면 받는 사람을 바꿔) · 결과를 바꾸는 업무 규칙·제약 값 · 데이터 해석만. 첫 목록에 이미 적은 질문은 번호만. '구체적으로'라는 답을 받은 질문은 후보마다 쪼갠다
- 상대가 모르는 것(비용·금액 등)은 한 번 묻고, 모르면 (추정)으로 두고 `docs/DECISIONS.md` 에

## 기준 확인 (계획 직후 한 번)
- DECISIONS 의 Codex 추정 가운데 결과 숫자를 가장 크게 바꾸고 아직 실무자가 답하지 않은 업무 값 2개 이하를 숫자와 함께 한 메시지로(없으면 보내지 않는다. '○○는 △△로 계산했고 그러면 결과가 □□입니다. 이렇게 하려는데 괜찮을까요?'). 이미 답한 성공 기준·알고리즘·기술 선택은 넣지 않는다('방법은 개발하시는 분이'로 끝난다)
- 승인이면 AGREEMENT 데이터·평가 규칙에 '담당자 승인(시각)', DECISIONS 정한 쪽은 실무자. 다른 안을 고르면 그 안으로 STATUS 를 고친다
- '정해진 것 없다'는 답에는 우리 안 하나를 한 문장으로 제안해 같은 방식으로 승인을 받는다

## 묻지 않는 것 (정해서 `docs/DECISIONS.md` 표에 한 줄. AGREEMENT 에 표를 만들지 않는다)
- 앞뒤 행·표기만 보면 정해지는 것: L2=l2, 날짜 순서, 표기만 다른 이름
- 계산 세부: 주·일 경계 · 기준 시각 · 이미 답한 규칙의 시작 시점 · 동점 처리 · 우리 방법의 값(알림 묶음·감지 임계값). 결과를 바꾸는 업무 규칙·제약 값과 실무자가 정한 판정 기준의 숫자(몇 분 안·몇 번 이상·연결·종료 간격), 예측의 검증 기간·목표 둘이 맞설 때 기준점 고르는 규칙은 여기 넣지 않고 묻는다
- 규칙으로 바로 계산되는 값(합계·비율)의 오표시 허용. 오차 기준 하나면 된다

## 데이터 함정 목록 (질문 고를 때)
- 단위가 바뀐 시점 · 환산 기준
- 시간대 표기 없는 시각 · 기록 시각과 실제 사건 시각의 차이
- 같은 대상의 다른 표기 (이름·코드)
- 중복 기록 (재전송·이중 기재)
- 빈 칸의 뜻 (끊김·정지·해당 없음)
- 기준값·규칙이 바뀐 날짜
- 정상인데 값이 튀는 구간 (점검·교체·시작 직후)
- 기간 밖 행 (기준일 뒤 날짜·미래 기록. 거르면 거른 건수를 남긴다)
- 묶음마다 다른 규칙 (조·등급·구역·종류마다 맡을 수 있는 것)
- 정답·사건으로 볼 행의 조건 (유형 열 값)

## 질문 쓰는 법
- 한 질문에 한 주제, 한두 문장. 번호를 붙여 첫 메시지에 2~3개, 답이 첫 질문에만 오면 그 뒤로는 한 메시지 한 질문. 목록으로 묶거나 '무엇인가요'·'…도 확인해 주세요' 꼬리를 붙이지 않는다
- 닫힌 질문 꼴: '○○인 경우도 바로 △△하면 되나요?'(예/아니요와 처리 기준으로 답할 수 있게). 기술 스택·저장 방식은 묻지 않는다(업무 맥락만). 답이 돌면 보기 2개 → 실제 행 하나 → 내 이해 확인 순으로 바꿔 묻는다
- 데이터 사실을 넣는다. 예: "maintenance_log 에 같은 시각 같은 설비 행이 두 개인데 같은 일인가요?"
- 성공 숫자 질문에는 데이터 사실을 억지로 붙이지 않는다
- 처음 질문에는 '자동화'·'AI' 같은 해법 낱말을 쓰지 않는다. 실제 질문은 사람이 메신저로 한다

## 답 정리
- 이 단계에서는 `docs/AGREEMENT.md` · `docs/DECISIONS.md` 만 고친다 (VERIFICATION·STATUS 는 손대지 않는다). 구현을 시작한 뒤 온 요구 변경이면 STATUS 의 영향받는 단위와 '나란히 계약'도 고친다
- 기준 하나가 바뀌면 같은 숫자를 쓰던 다른 값(연결·종료 간격·임계값)을 찾아 질문에 넣는다. 옛 기준 숫자는 '변경 전'으로 한 줄 남긴다
- 인터뷰 기록 표에 질문 하나당 한 줄: 질문 · 답 요지(40자) · 누가. 답 원문을 붙이거나 문장마다 줄을 나누지 않는다. 숫자·이름·조건은 답에 쓴 그대로
- 문제 · 성공 기준 · 범위 · 데이터·평가 규칙 가운데 바뀐 칸만 고친다
- 답으로 풀린 차이 줄은 지운다. 차이 칸에는 아직 모르는 것만 남긴다
- 말과 데이터가 다르면 차이 칸에 한 줄로 적고 다음 질문으로 돌린다
- 답은 5줄 이내: 확정이면 '확정'과 성공 기준 2줄, 아니면 남은 것과 다음 질문. 확정은 결과를 바꾸는 규칙·제약 값 가운데 아직 안 물은 (추정)이 없을 때만
