# 과제 파악과 실무자 인터뷰

실무자는 묻는 것만 답하고 요구를 한 번에 다 알려 주지 않는다. 데이터에서 본 사실로 좁혀 묻는다.

## 처음 파악
- README · 제공 파일 목록 · `docs/DATA_PROFILE.md`(없으면 `python3 .agents/kit/templates/data/profile_data.py <데이터 파일>` 결과)만 읽는다. 큰 데이터는 통째로 열지 않는다
- `docs/AGREEMENT.md` 과제 요구 표: 필수 기능 · 제출물·파일명 · 실행 방법 · 제약. 칸은 한 줄(40자 안팎), 모르는 칸은 (추정)
- 데이터 점검의 '확인할 것'을 차이 칸에 옮기고, 그중 결과를 바꾸는 것부터 질문으로 만든다

## 질문 순서
1. 최근 실제 사례 한 건: 언제 · 무엇이 · 어떻게 처리됐나
2. 지금 쓰는 방법과 가장 불편한 점
3. 성공 숫자: 어떤 지표가 얼마가 되면 성공인지 · 거짓 알림·오류 허용 범위
4. 누가 언제 결과를 보고, 누가 결정하는지 · 결과물 형식
5. 범위: 이번에 꼭 · 하지 말 것 · 쓰지 말 데이터
6. 데이터 해석: 아래 함정 목록 중 점검에서 걸린 것
7. 상대가 모르는 것 확인(비용·금액 등). 모르면 (추정)으로 두고 결정 기록에 남긴다

## 데이터 함정 목록
- 단위가 바뀐 시점 · 환산 기준
- 시간대 표기 없는 시각 · 기록 시각과 실제 사건 시각의 차이
- 같은 대상의 다른 표기 (이름·코드)
- 중복 기록 (재전송·이중 기재)
- 빈 칸의 뜻 (끊김·정지·해당 없음)
- 기준값·규칙이 바뀐 날짜
- 정상인데 값이 튀는 구간 (점검·교체·시작 직후)
- 정답·사건으로 볼 행의 조건 (유형 열 값)

## 질문 쓰는 법
- 한 질문에 한 주제, 한두 문장. 묶음 질문을 만들지 않는다
- 데이터 사실을 넣는다. 예: "maintenance_log 에 같은 시각 같은 설비 행이 두 개인데 같은 일인가요?"
- 처음 몇 질문에는 '자동화'·'AI' 같은 해법 낱말을 쓰지 않는다
- 다음에 물을 질문 2~3개를 사람에게 제안한다. 실제 질문은 사람이 메신저로 한다

## 답 정리
- 인터뷰 기록 표에 질문 · 답 요지 · 누가. 답 원문은 바꾸지 않는다
- 문제 · 성공 기준 · 범위 · 차이 칸 가운데 바뀐 칸만 고친다
- 말과 데이터가 다르면 차이 칸에 둘 다 적고, 어느 쪽을 따를지 질문으로 돌린다
