# 검증과 제출 점검

## 검증할 때
- `docs/VERIFICATION.md` 한 줄씩: 대상 · 명령 · 기대 · 실제 · 판정. 40줄 이하
- 숫자 결과는 다른 계산(직접 합계 · 표본 한 건 손계산 · 평가 함수를 쓰지 않는 별도 계산)으로 한 번 더 맞춘다
- 성공 기준 지표는 목표 값과 나란히 적는다 (예: 4/5건 · 목표 4건 이상 · 통과)
- 실패하면 원인 한 줄과 고친 커밋을 적고, 처음 실패한 그 명령으로 다시 돌린 결과까지 같은 줄에
- 정상 경로 말고 실패 경로 1~2개(잘못된 입력 거절 · 저장 실패 · 동시 저장)도 한 줄씩
- 끝나면 커밋

## 문서·제출 점검 (한 요청으로)
0. 깨끗한 확인: 서버가 없으면 `d=$(mktemp -d)/c && git clone -q . "$d" && cd "$d"` 에서 README 명령을 그대로 돌린다. 서버가 있으면 이미 승인된 `python3 verify.py clean` 처럼 clone 을 안에서 하는 검사로, 포트는 PORT=0. 작업 폴더 안에 복사본·worktree 를 만들지 않는다
1. `docs/AGREEMENT.md` 과제 요구 표와 제출 파일명 · 경로 · 실행 방법 대조
2. README: 실행 한 줄(실제로 돌린 python3·python 그대로) · 구조 · 성공 기준 결과 숫자 · 한계
3. 서버가 있으면 `0.0.0.0` 과 포트가 README 와 같은지. 사람이 띄운 서버의 포트로 검사하지 않는다. 포트 충돌은 이 환경 사정이라 README·DECISIONS 에 적지 않는다
4. DECISIONS · STATUS · VERIFICATION 의 숫자가 실제 출력 · `git log` 와 맞는지. 표 밖 긴 설명은 지운다
5. 지어낸 값 · 예시 값 · 쓰지 않는 틀 파일 · 실험 파일 · 복사본이 작업 공간에 남아 있지 않은지(확인 질문은 작업 공간 파일로 만들어진다)
6. 캐시·임시 생성물은 `.gitignore` (지우지 않는다). 제출 결과 파일(보고서 HTML 등)은 무시하지 않고 커밋
7. 커밋 뒤 `git status --short` 가 비었는지 (지침 파일 포함)
- 5분 안에 못 고칠 것은 고치지 않고 목록으로

## 답
- 점검 결과 5줄 이내: 고친 것 · 남은 것 · 결과 숫자
- 사람이 '브리핑'을 시키면(카드 07) 파일 없이 답으로 30줄 이내, 카드 07 의 ①~⑨ 차례 그대로: 문제·성공 기준·결과 숫자 · 방법 수준(버린 대안이 안 되는 이유 숫자) · 구조와 데이터 흐름(파일·모듈 · 상태 위치) · 그 밖에 결과를 바꾼 결정 전부(넣은 값·뺀 값 · 왜, 추정뿐이면 '기록된 이유 없음' · 버린 대안, 없으면 '없음' · 정한 쪽) · 구현·검증한 것과 가정 · 실무자 답마다 코드에서 한 일(바꾼 것 · 그대로 둔 것 · 걸린 행 수) · 깨지는 조건과 장애·동시 수정 때 동작 · AI 제안을 받아들임·고침·버림 2건 · 약한 곳마다 파급과 다음 검증. 사람은 작업 중에 결정을 따라가지 않았다고 보고 처음 듣는 사람에게 설명하듯 쓴다. DECISIONS 와 git log 에 없는 것은 쓰지 않는다

## 독립 합격 검사 (검사 대화, 카드 05)
- `check_acceptance.py` 하나만 만든다. 기준은 AGREEMENT 성공 기준·과제 요구·STATUS 완료 조건·제출물 형식. 구현 코드를 읽어 맞추지 않는다
- 항목마다 '기대 · 실제 · 통과/실패/확인 불가' 한 줄을 찍고 끝에 통과·실패·확인 불가 수. 결과 파일이 없으면 실패로 보이고 멈추지 않는다. 정답이 없거나 구현을 봐야만 아는 항목은 확인 불가로 세고 실패에 넣지 않는다(나머지가 다 통과면 종료 0)
- 구현 대화는 이 파일을 고치지 않는다
- 구현과 숫자가 다르면 고치지 않고 차이를 보고한다(어느 쪽이 요구를 잘못 읽었는지는 사람이 정한다)
