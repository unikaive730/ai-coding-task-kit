# 계획과 위임

## 나누는 기준
- 한 단위 = 실행해서 확인할 수 있는 결과 하나 (데이터 정리 표 하나 · 계산 하나 · 화면 하나 · API 하나)
- 30분이 넘어 보이면 더 나눈다. 남은 시간의 20%는 검증·문서·제출에 남긴다
- 성공 기준 지표를 계산해 보여 주는 단위를 반드시 넣는다

## 순서
1. 데이터 읽기·정리 (단위·시간대·이름·중복을 합의대로 맞춘 표) - 이후 모든 단위의 바탕
2. 핵심 기능 한 줄기를 끝까지 (입력 → 처리 → 출력)
3. 성공 지표 계산과 대조
4. 결과 화면·보고서 · README
5. 남는 시간에 보조 기능

## docs/STATUS.md 형식
| 순서 | 단위 | 파일 | 완료 조건(명령 → 기대) | 나란히 | 상태 | 커밋 |
|---|---|---|---|---|---|---|

## 요청 틀 (사람 → 에이전트, 에이전트 → 다른 세션)
- 목표: 무엇을 만들거나 고치는지 한 줄
- 맥락: 관련 파일 · 합의한 해석 · 오류 원문
- 제약: 고칠 파일 · 건드리지 말 것 · 표준 라이브러리 우선
- 완료 조건: 어떤 명령을 돌려 무엇이 나오면 끝인지

## 나란히 맡기기
- 고칠 파일이 겹치지 않는 단위만. 예: 계산 모듈과 화면 파일
- 사람이 터미널 탭을 하나 더 열어 codex 를 새로 띄우고 위 요청 틀로 맡긴다
- 다른 세션은 맡은 파일만 고치고 `docs/` 와 git 은 건드리지 않는다. 끝나면 3줄 보고
- 원래 세션에는 "○○ 파일은 다른 세션이 맡았으니 건드리지 마" 를 알린다
- 기다리는 동안 원래 세션은 검증·문서 단위를 한다

'구현 전부 끝내 줘'처럼 한 번에 맡기지 않는다. 고치는 데 시간이 더 든다.
