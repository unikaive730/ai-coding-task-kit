# 계획과 위임

## 나누는 기준
- 한 단위 = 실행해서 확인할 수 있는 결과 하나 (데이터 정리 표 하나 · 계산 하나 · 화면 하나 · API 하나)
- 30분이 넘어 보이면 더 나눈다. 단위는 3~4개, 시간은 일 크기대로 적고 남은 시간을 다 채우지 않는다. 남은 시간의 20%는 검증·문서·제출에 남긴다
- 새 파일은 결과물에 필요한 만큼만. 검증 스크립트는 하나로 묶는다. 틀은 `.agents/kit/templates/` 에서 복사
- 성공 기준 지표를 계산해 보여 주는 단위를 반드시 넣는다
- 단위마다 테스트는 핵심 3~5개
- 합의 문서에 남은 (추정)은 여기서 정해 `docs/DECISIONS.md` 표에 한 줄씩

## 순서
1. 데이터 읽기·정리 (단위·시간대·이름·중복을 합의대로 맞춘 표) - 이후 모든 단위의 바탕
2. 핵심 기능 하나를 입력부터 처리·출력까지 끝낸다
3. 성공 지표 계산과 대조
4. 결과 화면·보고서 · README
5. 남는 시간에 보조 기능

## docs/STATUS.md (40줄 이하, 표 밖 설명은 10줄 이하, 완료 조건 칸은 명령 하나 → 기대 하나)
| 순서 | 단위 | 파일 | 완료 조건(명령 → 기대) | 나란히 | 상태 | 커밋 |
|---|---|---|---|---|---|---|

## 나란히 맡기기
- 고칠 파일이 겹치지 않는 단위만. 예: 계산 모듈과 화면 파일
- 계약은 STATUS '나란히 계약' 칸에 10줄 이내: 함수 이름 · 입력 · 반환 한 줄씩과 열 이름만
- 사람이 터미널 탭을 하나 더 열어 codex 를 새로 띄우고 맡긴다
- 맡은 대화는 자기 파일만 고치고 `docs/` 는 건드리지 않는다. 끝나면 자기 파일만 `git add` 해서 커밋(`index.lock` 이면 잠깐 뒤 다시), 3줄 보고
- 원래 대화도 자기 파일만 `git add` 해서 커밋한다. 기다리는 동안 다른 단위·검증을 한다

## 하지 않는 것
- '구현 전부 끝내 줘'처럼 한 번에 맡기기. 고치는 데 시간이 더 든다
- 계획 단계에서 코드·HANDOFF 쓰기
- 답은 계획 5줄 요약까지
